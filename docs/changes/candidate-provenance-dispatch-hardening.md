# Candidate Provenance and Dispatch Hardening

- **Date**: 2026-10-28
- **PR**: Working tree
- **Branch**: `main`
- **Status**: open
- **Commits**: —

## Why

Verified prediction values from imported external artifacts could enter candidate selection, while user approval or preflight could authorize untracked candidate files without a supported promotion evaluation. Raw provider dispatch scripts were also not surfaced as a lock condition.

## What changed

- Added the shared three-value prediction provenance contract and derived eligibility helper.
- Recorded local-run provenance, marked external imports ineligible, and prevented journal synchronization from treating verification as eligibility.
- Bound candidate manifests to source artifact and prediction hashes and rejected external predictions before candidate construction or blend optimization.
- Removed untracked-file authorization shortcuts, required an explicit promotion rule for continuation dispatch, and added a backdoor script scanner, CLI report, HUD finding, and dispatch blocker.
- Documented the contract and continuation-submission rule.

## Approach

Keep integrity verification separate from submission eligibility. Provenance is checked at the artifact boundary before prediction files are consumed. The dispatch scanner reports root and scratch Python files; the submission gate blocks active unacknowledged findings.

## Evidence

Pending requested lint and smoke verification.

## Impact & follow-ups

Candidate decision-evaluation receipts are not yet a distinct candidate evidence type in the existing decision-rule system; current dispatch requires the supported evaluation path available for run evidence. Reproduced external-code execution receipts are not generated by the current runner and therefore remain unresolved rather than implicitly trusted.
